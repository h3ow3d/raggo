# raggo

**raggo** is a secure, local-first agentic RAG system with pluggable domain packs.

Originally built as `rag-flight-lab` for flight operations analysis, it has been
refactored into a generic core with pluggable domains. The system demonstrates:

- Local model inference (no external APIs at runtime)
- pgvector for vector search
- Safe SQL tools (no arbitrary query generation)
- Intent-driven agent orchestration
- Docker-based security isolation
- Domain-agnostic RAG architecture
- A React + Vite frontend served via nginx (Phase 6)

See `PROJECT_SPEC.md` for the specification and `AGENTS.md` for build instructions.


## Quick start

```bash
cp .env.example .env
docker compose up --build
```

Once the stack is up:

- Frontend dashboard: <http://localhost:3000>
- Backend health:     <http://localhost:8000/health>
- Backend stats:      <http://localhost:8000/stats>
- Domain info:        <http://localhost:8000/domain>

For Kubernetes installs see [`docs/install-kubernetes.md`](docs/install-kubernetes.md);
the chart at `helm/raggo/` brings up the full stack with the same
security posture (NetworkPolicies, non-root pods, internal-only model
services) and is published as an OCI artifact at
`oci://ghcr.io/h3ow3d/raggo/charts/raggo` by the Phase 6 release
pipeline.

The frontend (currently flights-domain-aware) has four pages:

- **Dashboard** — live counts of flights, logs, incidents, embedded /
  unembedded logs, plus a button to trigger an ingestion top-up.
- **Add Flight Log** — pick a flight, fill in log type / source system /
  severity / message / metadata JSON, and submit. The backend stores the
  log and immediately requests an embedding for it from the local
  embedding service.
- **Vector Search** — manual pgvector similarity search with optional
  severity and source-system filters.
- **Agent Chat** — ask the backend agent a natural-language question and
  see the answer, the retrieved evidence, and the full `agent_trace`.

The frontend talks **only** to the backend via `/api/*` (proxied by
nginx). It never reaches the embedding or generation services directly —
those live on the internal `model_net`.


The backend automatically:

1. Waits for PostgreSQL
2. Enables the `vector` extension
3. Loads the domain specified by `RAGGO_DOMAIN` (default: `flights`)
4. Runs the domain's init.sql if needed
5. Seeds domain data if empty
6. Starts background embedding ingestion

## Pluggable domains

raggo uses a **DomainPack** architecture. Each domain is a self-contained module
defining:

- Database schema (init.sql)
- ORM models
- Seed data generation
- Vector search resources
- Safe SQL tools
- Intent classification rules
- Prompts and evidence formatting
- Dashboard stats

Two example domains are included:

### `flights` domain
Flight operations analysis with:
- **Resources**: `flight_logs` (vector search over log entries)
- **SQL Tools**: `get_delayed_flights`, `get_flights_by_airport`, `get_incidents_by_severity`, etc.
- **Data**: ~5,000 flights, ~50,000 logs, ~500 incidents

### `support_tickets` domain
Customer support ticket analysis with:
- **Resources**: `ticket_messages` (vector search over messages)
- **SQL Tools**: `get_open_tickets`, `get_tickets_by_priority`, `get_messages_by_ticket`, etc.
- **Data**: ~200 tickets, ~1,000 messages

## Switching domains

Set `RAGGO_DOMAIN` in `.env` or as an environment variable:

```env
# Use flights domain (default)
RAGGO_DOMAIN=flights

# Or switch to support tickets
RAGGO_DOMAIN=support_tickets
```

Then recreate the stack:

```bash
docker compose down -v
docker compose up --build
```

**Important**: Domain data is persistent in the PostgreSQL volume. To switch domains,
use `down -v` to clear the volume, or point to a different database.

Each domain has its own:
- Schema (created by `domains/<name>/init.sql`)
- Seed data (generated by `domains/<name>/seed.py`)
- Vector resources, SQL tools, and agent rules

## Write your own domain

To create a new domain (e.g., `inventory`):

1. **Create directory structure**:
   ```
   backend/app/domains/inventory/
     __init__.py      # Assemble DOMAIN pack
     init.sql         # Schema with pgvector columns
     models.py        # SQLAlchemy ORM models
     seed.py          # has_existing_data() + seed_database()
     sql_tools.py     # SafeSqlTool tuple
     intent_rules.py  # IntentRule tuple + default_plan()
     prompts.py       # DOMAIN_CONTEXT + format_evidence()
   ```

2. **Implement required contracts**:
   - `models.py`: Define tables with `embedding` columns as `Vector(get_settings().embedding_dim)`
   - `init.sql`: CREATE TABLE statements (use `vector(384)` for embedding columns)
   - `seed.py`: Export `has_existing_data(session)` and `seed_database(session, force, seed)`
   - `sql_tools.py`: Export `SQL_TOOLS` tuple of `SafeSqlTool` instances with Pydantic arg models
   - `intent_rules.py`: Export `INTENT_RULES` tuple and `default_plan(question)`
   - `prompts.py`: Export `DOMAIN_CONTEXT` string and `format_evidence(evidence)` function
   - `__init__.py`: Assemble and export `DOMAIN` (a `DomainPack` instance)

3. **Define embeddable resources** in `__init__.py`:
   - Specify `model`, `embedding_column`, `evidence_projection` callable
   - Optionally add `joins` and `filter_specs` for search

4. **Set domain in environment**:
   ```env
   RAGGO_DOMAIN=inventory
   ```

5. **Launch**:
   ```bash
   docker compose down -v
   docker compose up --build
   ```

See `app/domains/flights/` or `app/domains/support_tickets/` for complete examples.

## Architecture

### Core modules (domain-agnostic)

```
backend/app/core/
  config.py         # Settings
  database.py       # SQLAlchemy session
  model_clients.py  # Embedding/generation HTTP clients
  domain.py         # DomainPack interface + load_domain()
  schemas.py        # Generic API request/response models
  vector_search.py  # Generic vector search
  ingestion.py      # Generic embedding ingestion
  safe_sql.py       # SafeSqlRegistry and executor
  agent/
    intent.py       # IntentPlan + RuleBasedIntentClassifier
    prompt.py       # build_prompt()
    orchestrator.py # Main agent run() pipeline
```

### Domain modules

```
backend/app/domains/
  flights/
    __init__.py      # DOMAIN pack
    init.sql         # flights, flight_logs, incidents tables
    models.py        # Flight, FlightLog, Incident ORM
    seed.py          # Generate ~50k flight logs
    sql_tools.py     # Flight-specific SQL tools
    intent_rules.py  # "delayed", "incident", etc.
    prompts.py       # Flight context and evidence formatter
  support_tickets/
    __init__.py      # DOMAIN pack
    init.sql         # support_tickets, ticket_messages tables
    models.py        # SupportTicket, TicketMessage ORM
    seed.py          # Generate ~200 tickets
    sql_tools.py     # Ticket-specific SQL tools
    intent_rules.py  # "open ticket", "high priority", etc.
    prompts.py       # Support context and evidence formatter
```

## API endpoints

### Core endpoints

- `GET /health` — Liveness probe
- `GET /stats` — Dashboard stats (shape depends on domain)
- `GET /domain` — Current domain metadata, resources, and tools

### Data endpoints

- `POST /ingest` — Run bounded embedding ingestion
  ```json
  { "limit": 1000, "batch_size": 128 }
  ```

- `POST /search/vector` — Vector similarity search
  ```json
  {
    "query": "login issues",
    "resource": "ticket_messages",
    "top_k": 10
  }
  ```

### Agent endpoint

- `POST /query` — RAG agent query
  ```json
  { "question": "Show me critical open tickets" }
  ```

  Returns:
  ```json
  {
    "answer": "...",
    "evidence": [...],
    "agent_trace": {
      "strategy": "vector_and_sql",
      "sql_calls": [...],
      "vector_query": "...",
      "retrieved_ids": {...}
    }
  }
  ```

## Example questions

These questions are the ones the contract test suite replays against
each domain pack. They're a deliberately minimal set that exercises
all three retrieval strategies (`sql_only`, `vector_only`,
`vector_and_sql`) and confirms the agent produces a grounded answer
plus a populated `agent_trace`. See
[`docs/agent.md`](docs/agent.md) for a per-strategy walk-through and
[`docs/domain-packs.md`](docs/domain-packs.md) for the contract these
questions encode.

### Flights pack

- _"Were there any critical safety incidents this week?"_ — hybrid;
  invokes `get_incidents_by_severity` and a vector search over flight
  logs.
- _"Which airports are most associated with delays?"_ — structured;
  invokes `get_top_delay_airports`.
- _"Why are flights delayed lately?"_ — semantic; vector search over
  flight logs.

### Support tickets pack

- _"Show me open tickets from this week."_ — structured; invokes
  `get_open_tickets`.
- _"Any critical urgent tickets we should escalate?"_ — hybrid;
  invokes `get_tickets_by_priority` plus vector search over ticket
  messages.
- _"I was charged twice on my last invoice."_ — semantic; vector
  search over ticket messages.

The full canonical list lives at
`backend/tests/contract/fixtures/<pack>/agent_questions.json`. Adding
or changing a question there immediately becomes part of the contract
the agent must satisfy.

## Security model

- **PostgreSQL** is not exposed to the host (internal `database_net` only)
- **Model services** are not exposed to the host (internal `model_net` only)
- Model services have:
  - No outbound internet access
  - `read_only: true` filesystem
  - `cap_drop: ["ALL"]`
  - `security_opt: ["no-new-privileges:true"]`
  - Offline-only operation (`HF_HUB_OFFLINE=1`)
- **No external AI APIs** at runtime (OpenAI, Anthropic, etc.)
- **No arbitrary SQL execution** — only safe, parameterised, allowlisted tools
- Backend bridges networks but only exposes port 8000 for development

## Models

### CPU mode (default)

Default models run on CPU:

```env
EMBEDDING_MODEL_NAME=sentence-transformers/all-MiniLM-L6-v2
EMBEDDING_DIM=384
GENERATION_MODEL_NAME=Qwen/Qwen2.5-0.5B-Instruct
```

Models are downloaded at **build time** and baked into containers. Runtime is
fully offline (`HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1`).

### GPU mode (optional)

```bash
docker compose -f docker-compose.yml -f docker-compose.gpu.yml up --build
```

Set `MODEL_RUNTIME=cuda` in `.env` for GPU-accelerated generation.

### Changing models

Update `.env`:

```env
EMBEDDING_MODEL_NAME=sentence-transformers/all-mpnet-base-v2
EMBEDDING_DIM=768

GENERATION_MODEL_NAME=meta-llama/Llama-3.2-1B-Instruct
```

**Important**: If you change `EMBEDDING_DIM`, you must recreate the database:

```bash
docker compose down -v
docker compose up --build
```

## Troubleshooting

### Domain not loading

Error: `ModuleNotFoundError: No module named 'app.domains.xyz'`

- Check `RAGGO_DOMAIN` matches a directory in `backend/app/domains/`
- Ensure `backend/app/domains/xyz/__init__.py` exists and exports `DOMAIN`

### Embedding dimension mismatch

Error: `expected 384 dimensions, not 768`

- Your `.env` changed `EMBEDDING_DIM` but the database schema is still old
- Solution: `docker compose down -v && docker compose up --build`

### Out of memory

- Default models are small (all-MiniLM-L6-v2 ~80MB, Qwen2.5-0.5B ~1GB)
- If using larger models, increase Docker memory limit or use GPU mode

### Seed data too large/small

Domain-specific. For `flights`:

```env
SEED_FLIGHT_COUNT=1000
SEED_LOG_COUNT=10000
SEED_INCIDENT_COUNT=100
```

For `support_tickets`, edit `backend/app/domains/support_tickets/seed.py`.

## Reset database

```bash
docker compose down -v
docker compose up --build
```

This clears all data, re-runs init.sql, and re-seeds.

## Container images

raggo images are published publicly to GitHub Container Registry under
`ghcr.io/h3ow3d/raggo/`. No `docker login` is required to pull, and no
image pull secret is required to install.

```bash
docker pull ghcr.io/h3ow3d/raggo/backend@sha256:<digest>
docker pull ghcr.io/h3ow3d/raggo/frontend@sha256:<digest>
docker pull ghcr.io/h3ow3d/raggo/postgres-pgvector@sha256:<digest>
docker pull ghcr.io/h3ow3d/raggo/embedding-model@sha256:<digest>
docker pull ghcr.io/h3ow3d/raggo/generation-model@sha256:<digest>
```

Release images are signed with cosign using a long-lived key pair. The
public key is committed at [`.github/cosign.pub`](.github/cosign.pub).
Verify any release image directly against the committed key:

```bash
cosign verify \
  --key https://raw.githubusercontent.com/h3ow3d/raggo/main/.github/cosign.pub \
  ghcr.io/h3ow3d/raggo/backend@sha256:<digest>
```

See [`docs/images.md`](docs/images.md) for the full image inventory,
tagging scheme, SBOM/provenance details, and the verification
procedure.

## Kubernetes install

raggo ships a first-class Helm chart under [`helm/raggo/`](helm/raggo)
that brings up the same stack on Kubernetes with the same security
posture as the Compose deployment: NetworkPolicies isolate the model
and database services, every pod runs as non-root with a
`RuntimeDefault` seccomp profile, root filesystems are read-only where
feasible, and capabilities are dropped.

Quick start (kind or any cluster):

```bash
helm install raggo ./helm/raggo \
  --namespace raggo --create-namespace \
  --set secret.values.postgresPassword="$(openssl rand -hex 16)" \
  --wait --timeout 20m

helm test raggo --namespace raggo
```

The chart is published as an OCI artifact at
`oci://ghcr.io/h3ow3d/raggo/charts/raggo` by the Phase 6 release
pipeline; until then, install from a local checkout as shown above.
GPU installs use the matching overlay:

```bash
helm install raggo ./helm/raggo -f ./helm/raggo/values-gpu.yaml \
  --namespace raggo --create-namespace
```

See [`docs/install-kubernetes.md`](docs/install-kubernetes.md) for
external-Postgres mode, Ingress configuration, air-gap installs, and
troubleshooting.
